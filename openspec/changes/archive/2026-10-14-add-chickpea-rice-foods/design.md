## Context

食物库种子数据（`src/services/foodService.ts` 的 `SEED_FOODS`，当前 26 条）仅在**库为空**（首启）时整体写入；非空库的升级路径只做一件事：按 canonical 中文名对 `portions IS NULL` 的既有行回填份量。因此向 `SEED_FOODS` 追加新条目，老用户覆盖安装后永远看不到新食物——v1.8.1 的教训已证明「种子仅库空写入」的字段必须配套升级回填，本次新增条目属于同类问题的行级版本。

两种新食物均为高频需求：白米饭（东亚用户日常主食）与鹰嘴豆（欧美/素食高频豆类），且都要求带生活化份量预设，Quick Log 检测到 portions 非空即自动启用份量模式，UI 零改动。

## Goals / Non-Goals

**Goals:**

- 新安装备首启即获得白米饭、鹰嘴豆（双语名/备注、营养值、GI、份量预设）。
- 覆盖升级（食物库非空）启动时幂等补齐缺失的新种子，且不覆盖用户同名自建/已编辑条目。
- 份量预设遵循既有 FoodPortion 双语锚点结构与克数约定，备份/恢复零改动往返。

**Non-Goals:**

- 不做数据库 schema 变更（portions 列 v1.8.0 已存在）。
- 不新增 UI、i18n key 或 Quick Log 交互（现有双模式自动生效）。
- 不调整既有 26 条种子的任何数值，也不处理「用户改过的种子行恢复官方值」。
- 不引入其他新食物。

## Decisions

### D1：鹰嘴豆归入「膳食纤维」分类，不写 gi 字段

鹰嘴豆与扁豆（Lentils，已在膳食纤维分类、无 gi）营养定位最接近：高蛋白高纤豆类。项目既有不变式（测试强制 + spec「低 GI 标注仅适用碳水分类」）规定 **gi 只出现在碳水分类**；UI 的 Low GI 标签也只对碳水分类派生。

- 方案 A（采纳）：归膳食纤维，gi 留空，在 notes 中体现「低 GI 稳血糖」语义。卡片自动获得 High Fiber 语义标签，与扁豆一致。
- 方案 B（否决）：归碳水并写 gi=28。会得到 Complex Carb + Low GI 双标签，但破坏「豆类归纤维」的分类心智，并需放宽 gi 仅碳水的测试不变式与标签派生规则，影响面更大。

白米饭无此问题：归碳水、gi=73，与主 spec 既有的「白米饭 gi=73 不标低 GI」场景完全对齐，使该假想场景落地为真实数据。

### D2：营养值取「熟重」口径，与份量锚点一致

- 白米饭（蒸熟）：116 kcal / P2.6 / F0.3 / C25.9 per 100g（中国食物成分表熟米饭口径），gi=73。
- 鹰嘴豆（水煮/罐头沥干）：164 kcal / P8.9 / F2.6 / C27.4 per 100g（USDA boiled 口径）。

Quick Log 以克数换算营养，份量锚点描述的也是熟食（碗/杯熟重），营养值必须同口径，否则估算偏差 2–3 倍。

### D3：份量锚点

沿用既有「碗/杯」双语锚点风格（参考藜麦 1/2 碗熟 90g / 1 碗熟 185g）：

- 白米饭：`1/2 碗（熟）` / `1/2 Bowl Cooked` = 75g；`1 碗（熟）` / `1 Bowl Cooked` = 150g（中式标准碗一平碗熟饭约 150g）。
- 鹰嘴豆：`1/2 杯（熟）` / `1/2 Cup Cooked` = 80g；`1 杯（熟）` / `1 Cup Cooked` = 160g（USDA 1 cup cooked chickpeas ≈ 164g，取整 160g 与半杯 80g 成整倍）。

### D4：非空库升级路径增加「缺失种子插入」

重构 `ensureSeedFoods()`：

1. 抽出单条插入助手 `insertSeedFood(db, seed, catId)`，新装批量插入与升级补齐共用同一条 INSERT（含双字段、portions JSON）。
2. 非空库分支先构建 `existingNames`（现存 canonical 中文名集合）：
   - portions 回填（v1.7→v1.8 一次性迁移）仅对**冻结的 16 个历史种子名 allowlist `PORTION_BACKFILL_V180`** 且库中存在的行执行；缺失种子跳过 UPDATE（下面整行插入已带 portions），新版本种子（白米饭/鹰嘴豆）永不进入 UPDATE 集合。
   - 对每个 `!existingNames.has(seed.zh)` 的条目，按分类定位（`idByZh ?? idByEn`）后插入。
   - 已存在同名（无论官方种子还是用户自建）一律跳过——只补「缺失」，绝不覆盖。
3. 全程幂等：第二次启动时所有种子均已存在，INSERT 数为 0；无 ALTER/迁移。

**为何需要冻结 allowlist（代码审查补充决策）**：用户自建食物创建时 portions 恒为 NULL 且无编辑入口；food_item 无 is_seed 来源列，无法按行区分「旧官方种子行」与「同名用户自建行」。若回填 UPDATE 覆盖新种子名，升级前已自建「白米饭」的用户会被注入官方份量预设且无法移除，违反 spec「同名用户条目优先」场景。历史事实提供了精确判据：白米饭/鹰嘴豆在 v1.8.3 前从未作为种子下发，库中同名行必为用户自建；而 16 个历史名字的 NULL 回填是 v1.8.0 已发布行为，allowlist 即该迁移的冻结快照，此后不再扩展（未来新种子同走「缺失即插入」）。曾评估「`AND name_en = 官方英文名` 鉴别」，但旧库迁移只加列不回填 name_en（v1.4.x 直升设备官方行 name_en 为 NULL），该方案会切断老设备的历史回填，否决。

分类定位与新装路径完全相同（分类表 5 条固定种子，库非空时分类必然已存在，但仍保留 `catId === undefined → continue` 防御）。

备选「按 version 记录种子版本号、只在版本升级时扫描」被否决：当前无种子版本元数据，引入它属过度设计；一次启动 28 条 SELECT 内存比对成本可忽略。

## Risks / Trade-offs

- [用户自建条目恰好命名「白米饭」/「鹰嘴豆」] → 插入按 canonical 名跳过，portions 回填 allowlist 也不含新名字，该用户条目营养值与 portions 均原样保留（spec「同名用户条目优先」场景）；代价是该用户拿不到官方条目，可接受。
- [种子总数断言过窄] → 现有测试断言数量区间 24–27，28 条会失败；实施时同步放宽为覆盖现状与小幅增减的区间（26–30）并更新用例描述。
- [升级插入重复执行产生重复行] → 插入前以 canonical 名内存集合判重，且插入随启动幂等；不依赖 DB 唯一约束（food_item.name 非唯一，支持用户自定义同名食物）。
- [熟重口径与部分用户按生米计量习惯不同] → 卡片 notes 与锚点均显式标注「（熟）/ Cooked」；精确克数模式仍在，用户可自行按实际克数记录。

## Migration Plan

1. 发布新版（建议 v1.8.3 / versionCode 28，app.json + build.gradle 三处同步）。
2. 新装：首启常规种子写入，自动包含 28 条。
3. 覆盖安装：首次启动 `ensureSeedFoods` 回填 portions 并插入 2 条缺失食物，随后各次启动为无操作。
4. 回滚：旧版本读取新行无任何不兼容（均为普通 food_item 行，portions 为既有列）；无需降级脚本。
